ÉTAPE 3 — EXTERNALISATION VERS UN STOCKAGE OBJET (GUIDE POUR LE COLLÈGUE)
==========================================================================

On part sur l'Option A : MinIO auto-hébergé via Docker.
C'est un serveur S3-compatible qui tourne en local dans un conteneur.
Pas besoin de compte cloud, pas de carte bancaire, tout reste en local.


CE QU'IL FAUT FAIRE (résumé)
-----------------------------

1. Déployer MinIO en Docker
2. Créer un bucket pour les sauvegardes
3. Configurer Restic pour qu'il utilise ce bucket comme backend S3
4. Faire une première sauvegarde vers MinIO et vérifier qu'elle est là
5. Mesurer les temps de transfert
6. Rédiger une comparaison MinIO vs cloud (pour le rapport)


ÉTAPE PAR ÉTAPE
---------------

1) DÉPLOYER MINIO

   Ajouter un fichier docker-compose.yml dans un nouveau dossier,
   par exemple pra/minio/docker-compose.yml :

   services:
     minio:
       image: minio/minio
       container_name: minio
       command: server /data --console-address ":9001"
       environment:
         - MINIO_ROOT_USER=minioadmin
         - MINIO_ROOT_PASSWORD=minioadmin123
       volumes:
         - minio_data:/data
       ports:
         - "9000:9000"    # API S3
         - "9001:9001"    # Console web
       restart: unless-stopped

   volumes:
     minio_data:

   Lancer avec :
     cd pra/minio
     docker compose up -d

   La console web est accessible sur http://localhost:9001
   Login : minioadmin / minioadmin123


2) CRÉER LE BUCKET

   Deux options :

   a) Via la console web (http://localhost:9001) :
      Buckets > Create Bucket > nom : "restic-backup" > Create

   b) Via la ligne de commande avec le client mc (MinIO Client) :
      docker run --rm --entrypoint sh minio/mc -c "
        mc alias set local http://host.docker.internal:9000 minioadmin minioadmin123 &&
        mc mb local/restic-backup
      "

      Ou plus simple, installer mc sur la machine :
        sudo pacman -S minio-client
        mcli alias set local http://localhost:9000 minioadmin minioadmin123
        mcli mb local/restic-backup

      (Sur Arch le binaire s'appelle "mcli" pour ne pas entrer en
       conflit avec Midnight Commander)


3) INITIALISER LE DÉPÔT RESTIC SUR MINIO

   Restic a besoin de ces variables d'environnement pour parler à MinIO :

     export AWS_ACCESS_KEY_ID=minioadmin
     export AWS_SECRET_ACCESS_KEY=minioadmin123
     export RESTIC_REPOSITORY=s3:http://localhost:9000/restic-backup
     export RESTIC_PASSWORD_FILE=/home/thomas/pre-sae-ccd-v2/pra/secrets/restic-password

   Puis initialiser le dépôt distant :

     restic init

   Ça devrait afficher "created restic repository ... at s3:http://..."

   IMPORTANT : le mot de passe Restic doit être LE MÊME que celui du
   dépôt local (fichier pra/secrets/restic-password). C'est nécessaire
   si on veut copier des snapshots entre les deux dépôts.

   En fait non, correction : Restic ne copie pas entre dépôts de cette
   façon. Chaque dépôt est indépendant. Mais par simplicité, autant
   utiliser le même mot de passe pour les deux.


4) FAIRE UNE PREMIÈRE SAUVEGARDE VERS MINIO

   On peut soit :

   a) Relancer le script backup.sh en changeant RESTIC_REPOSITORY :
      (il faudra adapter le script pour supporter les deux backends)

   b) Ou plus simple pour tester : faire un backup manuel

      export AWS_ACCESS_KEY_ID=minioadmin
      export AWS_SECRET_ACCESS_KEY=minioadmin123
      export RESTIC_REPOSITORY=s3:http://localhost:9000/restic-backup
      export RESTIC_PASSWORD_FILE=/home/thomas/pre-sae-ccd-v2/pra/secrets/restic-password

      # Lancer le backup du même staging directory que le script local
      # (ou refaire un dump + export des volumes manuellement)
      restic backup /tmp/restic-staging --tag bookstack --tag s3 --verbose

   Vérifier que le snapshot est bien là :
      restic snapshots

   Vérifier dans la console MinIO (http://localhost:9001) que le bucket
   contient des fichiers (dossiers data/, index/, keys/, snapshots/).


5) MESURER LES TEMPS DE TRANSFERT

   Chronomètre simple :
     time restic backup /tmp/restic-staging --tag benchmark

   Noter :
   - La durée totale
   - La taille du snapshot (affiché par restic)
   - Le volume stocké (visible dans la console MinIO ou avec "mcli du")

   Comme MinIO tourne en local (localhost), les temps seront très rapides.
   Mentionner dans le rapport que dans un vrai scénario hors site, la
   latence réseau et le débit seraient les facteurs limitants.


6) COMPARAISON MINIO VS CLOUD (pour le rapport)

   Voici les points à aborder :

   COÛT
   - MinIO : gratuit, open source, tourne sur ta propre machine
   - Cloud (Backblaze B2, Scaleway, GCP) : souvent gratuit en dessous
     d'un certain quota (10 Go chez Backblaze B2, 75 Go chez Scaleway),
     puis facturation au Go/mois + frais d'egress (téléchargement)

   COMPLEXITÉ DE MISE EN OEUVRE
   - MinIO : un docker compose up et c'est fait, pas de compte à créer,
     pas de configuration réseau complexe
   - Cloud : créer un compte, configurer les accès IAM/API keys,
     gérer les régions, potentiellement configurer du HTTPS

   SOUVERAINETÉ DES DONNÉES
   - MinIO : les données restent sur ta machine, tu as le contrôle total
   - Cloud : les données sont chez un tiers (USA pour Backblaze,
     France/Europe pour Scaleway). Sujet sensible pour des données
     d'entreprise ou universitaires

   PERFORMANCES
   - MinIO local : latence quasi nulle, débit limité par le disque local
   - Cloud : latence réseau (dizaines de ms), débit limité par la
     connexion internet. Plus lent pour les backups et les restaurations

   FIABILITÉ / DISPONIBILITÉ
   - MinIO local : un seul disque, pas de redondance. Si la machine
     tombe, MinIO tombe aussi. En production il faudrait du MinIO
     distribué (multi-nœuds) ou un RAID
   - Cloud : redondance gérée par le fournisseur (réplication multi-DC),
     SLA de 99.9%+

   CONCLUSION POUR LE RAPPORT
   MinIO est le choix adapté pour un projet pédagogique : simple,
   gratuit, et ça permet de comprendre le fonctionnement du stockage
   objet S3. En production, on opterait pour un cloud public (ou un
   MinIO distribué sur site distant) pour avoir une vraie séparation
   géographique et de la redondance.


INTÉGRATION AVEC LE SCRIPT BACKUP.SH EXISTANT
----------------------------------------------

Pour l'étape 4 (automatisation), le script orchestrateur devra faire
la sauvegarde vers les DEUX backends (local + MinIO). On pourra soit :

- Faire deux "restic backup" séparés (un vers chaque repo)
- Ou utiliser "restic copy" pour copier les snapshots du dépôt local
  vers le dépôt MinIO (plus efficace, mais nécessite restic >= 0.14)

La commande restic copy :
  restic -r /mnt/restic-backup/repo copy --to-repo s3:http://localhost:9000/restic-backup

Ça copie les snapshots du repo local vers le repo S3 sans refaire
le backup depuis zéro.


CREDENTIALS À SAUVEGARDER
--------------------------

Ajouter dans pra/secrets/ (gitignored) un fichier avec les credentials
MinIO, par exemple pra/secrets/minio-credentials :

  AWS_ACCESS_KEY_ID=minioadmin
  AWS_SECRET_ACCESS_KEY=minioadmin123

Et le sourcer dans les scripts avec : source pra/secrets/minio-credentials
